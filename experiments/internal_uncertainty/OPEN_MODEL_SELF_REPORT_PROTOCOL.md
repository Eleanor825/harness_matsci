# Open-Source Model Self-Reported Confidence Protocol

## Hypothesis

An open-source instruction model's explicitly reported confidence can provide
an actionable uncertainty feature for a scientific judge harness. After
calibration, adding this feature to a VoI harness should improve fixed-budget
scientific action selection over the same model's direct judgment alone.

This experiment does **not** claim to measure intrinsic model uncertainty. The
signal is generated by asking the model to report confidence. Intrinsic
uncertainty is reserved for the separate logit-access experiment.

## Required model output

Use one model and one prompt template for every split. Require strict JSON:

```json
{
  "decision": "execute|defer_or_stop",
  "confidence": 0.0,
  "uncertainty": 0.0,
  "expected_utility": 0.0,
  "rationale": "short explanation"
}
```

The prompt must define confidence as the probability that executing the
proposed action is worthwhile under the benchmark's action label, rather than
confidence in the wording of the answer. `uncertainty` must be constrained to
`1 - confidence` for the primary analysis, with free-form uncertainty treated
as a secondary ablation.

## Frozen protocol

1. Generate model responses once and cache raw prompts, raw outputs, parse
   status, model identifier, revision, decoding parameters, and record IDs.
2. Keep the foundation model frozen; only the harness may be optimized.
3. Split records into train, feedback, acceptance, and untouched test sets.
4. Fit calibration and fusion weights using train/feedback only.
5. Select RHI mutations using feedback and acceptance only.
6. Evaluate every final method on the untouched test set under the same fixed
   action budget.

## Main comparisons

```text
M0  direct open-model judge score
M1  direct judge + calibrated self-reported confidence
M2  M1 + static VoI routing
M3  M2 + RHI evolution with guarded acceptance
M4  M2 + RHI evolution with always-accept (mechanism control)
M5  M2 with confidence permutation within task (signal control)
```

The primary causal comparison is `M2` versus `M5`, while `M3` versus frozen
`M2` tests whether RHI adds value beyond static VoI. `M4` is not a preferred
method; it isolates the effect of acceptance policy.

## Metrics

Primary:

- oracle-normalized net utility at fixed action budget;
- risk-adjusted utility;
- selective risk.

Secondary:

- ECE and Brier score of reported confidence;
- Risk@10%;
- hit rate and coverage;
- execute, verify, stop, and fallback rates;
- worst-regime utility;
- number of model calls and estimated cost.

## Required controls

- Compare at least three random seeds with non-overlapping test partitions or
  explicitly report a shared-test limitation.
- Use temperature 0 for the primary run and one nonzero-temperature stability
  run if compute allows.
- Never use test labels to calibrate confidence, select the LLM/harness blend,
  propose mutations, or accept revisions.
- Report parse failures and missing-confidence fallbacks.
- Keep self-reported confidence separate from logit confidence in all tables
  and prose.

## Interpretation boundary

If `M1`/`M2` improves over `M0`, the result supports the usefulness of a
model-reported confidence feature. If `M3` improves over frozen `M2`, it
supports self-evolution of the executable harness. Neither result alone
establishes that the signal is intrinsic uncertainty; that requires the
separate candidate-token-logit experiment.
